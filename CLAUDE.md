# CLAUDE.md

Guidance for Claude working in this repo. The documents in `docs/` are the source of truth for what the engine must do. Read the relevant one before changing behavior or interfaces.

## Project

logix-engine is an open source FPGA engine: one Rust binary per platform that exposes FPGA operations as MCP tools over stdin/stdout. Hosts (Logix IDE and other Logix frontends, other FPGA tools, IDE extensions, CI, AI agents) launch it as a child process. It drives existing open source tools (Yosys, nextpnr, openFPGALoader and others) and never implements a toolchain itself.

| Document | Read it when |
| --- | --- |
| [docs/requirements.md](docs/requirements.md) | Deciding what the engine must or must not do |
| [docs/architecture.md](docs/architecture.md) | Adding components, dependencies or tests |
| [docs/tool-api.md](docs/tool-api.md) | Adding or changing a tool, field, error or progress report |

## Current scope: Milestone 2

Milestone 1 (iCE40, seven tools, tested on an Alhambra II) is done. Milestone 2 is Logix IDE running on the engine without losing any feature it had: Table 15 in [docs/requirements.md](docs/requirements.md#acceptance-and-phasing) lists them (lint, test, simulate, format, graph, live tool output, and every board the IDE offers today across all four architectures; a board is dropped only for a very good, recorded reason). Examples aren't an engine feature: an example is a project, and project models are defined by the frontends, not the engine, so each frontend provides examples in its own model and source format. For AI sessions with no other requirements, the engine only suggests a default one (docs/tool-api.md, Default project model; a short form is in the server instructions in `src/server.rs`). It isn't a standard for frontends and hosts, and the engine needs no project file in any format. macOS arm64 only. Toolchain packages come from existing open source package releases, pinned in the manifest. Don't build later-phase features unless asked.

## Code and commands

- `src/main.rs`: the command line. Everything else is a library (`src/lib.rs`), so tests can use it.
- `src/server.rs`: the MCP server (rmcp). `src/tools/`: one file per tool, each with its input and output types and an `EngineTool` impl. Add a tool to `all_definitions()` and `call()` in `src/tools/mod.rs`.
- `src/errors.rs`: the error model. `src/paths.rs`: path checks. `src/logging.rs`: log files. `src/text.rs`: the text forms. `src/state.rs`: launch settings, engine version, protocol versions, platform.
- `src/packages/`: the package manager. `manifest.json` pins each package's release, file, size and SHA-256 per platform. To update a package, take the asset's size and digest from the GitHub release (`gh release view <tag> -R <owner>/<repo> --json assets`). `src/progress.rs`: progress by phase. `src/mcp_progress.rs`: sends progress as MCP progress notifications when the request has a progress token, and live tool output as `logix/output` notifications when the request's `_meta` asks for it, both in order before the result. Each tool gets a `Call` with the progress and output sinks and a cancellation token; tools that run programs pass `call.output` to the runner.
- `catalog/boards.json`, `catalog/fpgas.json`: the catalog, built into the engine; `src/catalog.rs` loads and checks it. This is the catalog's source: edit it here. It is the baseline, maintained here by hand: add or fix boards by editing these files (there is no importer). The catalog has iCE40, ECP5, Gowin and Xilinx (84 boards, 131 variants; the 14 dropped boards and why are in docs/requirements.md). A board is its name (different names are unrelated boards, even with identical hardware; each FPGA size is its own board, since pins can differ); its `variants` list the ways it can be programmed (one concept: there are no separate configurations), the first being the default (flash wherever the board has it, checked by a test), each with an `id` (`<connection>-<memory>`, checked by a test; what `board_variant` names in requests), its `connection` and `memory` (the two standard dimensions every board has, from the engine's list `STANDARD_DIMENSIONS` with labels and help; `get_catalog` adds the board's derived `dimensions`; `unspecified` connection when unknown, with a maintainer note; memory follows from the command), the programmer, `args`, `usb` and its own `tested` (false only when its programming changed from the original command and wasn't tried on hardware, or it's new; a change rated low risk, checked in the programmer's source, keeps it true, such as `--busdev-num ${BUS}:${DEV}` on every FTDI openFPGALoader command and `-p ${PORT}` on every dfu-util command, which tests check), optional `user_notes` (for users: warnings and missing information, such as a USB filter that matches other boards) and `maintainer_notes` (for maintainers: where settings come from and why they changed; never returned by `get_catalog`; required when `tested` is false). A variant changes only how the board is programmed: all variants of a board have the same FPGA and the same pin file (a version with an LED or any signal on another pin is a different board); tools take an optional `board_variant` (a variant ID); a different variant means a full rebuild (the build record's board includes the variant). The rules are in docs/requirements.md, Boards and board variants. The engine supports the programmers in `PROGRAMMERS` (openfpgaloader, iceprog, dfu-util, icesprog; all from oss-cad-suite). Never write "Apio" in catalog data. **Never run a programmer by hand to see its messages while a board it could reach is connected**: icesprog wrote to the user's iCESugar-Pro that way.
- FPGAs in `catalog/fpgas.json` have a `jtag_idcode` (ECP5, Gowin, Xilinx), taken from openFPGALoader 1.2.0's `src/part.hpp` by part number (Gowin by `packer_device`), never by size; a test checks every JTAG board's FPGA has one. Before writing over JTAG, `program_board` runs openFPGALoader `--detect` with only the variant's connection options (`CONNECTION_OPTIONS` in `src/program.rs`, so it can't write) and refuses another FPGA. Update the ID codes when the openFPGALoader version changes.
- `src/board.rs`: board inputs (catalog ID or full definition), resolved into the full board the build record keeps. `src/build/`: the build (each architecture's standard open source flow: yosys, nextpnr-ice40 and icepack for iCE40; yosys, nextpnr-ecp5 and ecppack for ECP5; yosys, nextpnr-himbaechel and gowin_pack for Gowin; yosys, then nextpnr-xilinx, fasm2frames and xc7frames2bit from the `openxc7` package, for Xilinx), up-to-date check, build record, and `clean.rs` for `clean_build`. `src/build/parse.rs` reads tool output into diagnostics; its tests use real tool output. `src/sim/`: lint (Verilator), testbenches (`testbench.rs`: iverilog and vvp, for test and simulate) and GTKWave (`gtkwave.rs`: default layouts, detached launch), with the standard options and the FPGA's primitive models; `src/sim/parse.rs` reads Verilator and Icarus output into diagnostics, tested with real output. `src/format.rs`: the `format` tool's work (Verible's formatter in place; its tests use real Verible output). `src/graph.rs`: the `graph` tool's work (yosys `show` and Graphviz's `dot` from the toolchain package). `src/commands.rs`: the `commands` list in results (each program run, with a shell line that reruns it); `run_watched` and `program_board` record into `Call::commands`. `src/runner.rs` runs tools with a minimal environment and stops the process tree on cancel (SIGTERM, then SIGKILL after 2 s).
- `src/devices.rs`: USB scanning with libusb built in (rusb, vendored), device IDs (opaque, from the USB port path), board matching with a match level, `strong`, `possible` or `weak` (`MatchLevel`: what the match means for the user, never its cause; hosts only show and compare levels; the criteria, including `FACTORY_DEFAULT_NAMES` and `FEW_BOARDS`, are internal and may change without notice, kept in docs/requirements.md for maintainers and never in the tool API; against the catalog and the request's custom boards, at request time) and finding the chosen device; `program_board` requires a device ID from `list_devices`. `src/program.rs`: programmer commands, progress from programmer output, and failure classification, tested with the programmers' real messages. `list_devices` and `program_board` take the scan as a parameter (`run_with`), so tests use fake device lists and a fake programmer; real boards are checked by hand.
- `build.rs` sets the engine version: the `LOGIX_ENGINE_VERSION` env var for releases (the release tag), otherwise today's UTC date.
- Tests: unit tests next to the code; `tests/cli.rs` (command line), `tests/mcp.rs` (end to end: launches the binary and talks MCP), `tests/schemas.rs` (published schemas), `tests/packages.rs` (package install against a local test server), `tests/build.rs` (real builds with the real toolchain, installed once into `target/tmp/test-engine`: the first test run downloads 650 MB, oss-cad-suite and openxc7; `scripts/clean.sh` deletes it; CI caches it), `tests/sim.rs` (lint, test and simulate with the same real toolchain), `tests/format.rs` (format with the real `verible` package, 8 MB, in the same engine folder), `tests/graph.rs` (graph with the real toolchain). `tests/designs/` holds small designs for tests and hand testing (not examples); tests copy them to a temporary folder. The ignored test `real_oss_cad_suite_install` downloads the real package (526 MB): `cargo test --test packages -- --ignored`, and `real_install_packages_with_progress` does the same through MCP with progress: `cargo test --test mcp -- --ignored`. Run them after changing the manifest, the install code or progress reporting.
- **Before committing, run `scripts/test.sh`.** After a deliberate schema change, run `scripts/update-schemas.sh` and review the diff in `schemas/tools.json`.
- Rust is pinned in `rust-toolchain.toml`. With Homebrew's rustup, `cargo` is in `/opt/homebrew/opt/rustup/bin`, which isn't on the PATH by default. Every script sources `scripts/_rust-env.sh`, which adds it when `cargo` isn't found.

## CI and releases

Same conventions as logix-ide, using the shared actions from `openlogix/.github` (`openlogix/.github/actions/<name>@v1`; that repo documents and tests them).

- **`test.yaml`**: on every push and pull request, manually, and daily at 00:00 UTC; a newer run for the same ref cancels the older one; matrix macos-15, macos-26, macos-latest, `fail-fast: false`, 30 min. Installs the pinned Rust, then runs `scripts/test.sh`.
- **`build-pre-release.yaml`** (on every push to `main`, daily at 00:00 UTC, and manually; a newer run cancels a running one), three jobs:
  - `prepare` (Ubuntu): release tag `yyyy-mm-dd` and package tag `yyyymmdd`, an early check that no stable release has that tag, repo info, and `BUILD-INFO.json` (with `engine-version` = the release tag) as the `build-info` artifact.
  - `build-darwin-arm64` (reusable `build-darwin-arm64.yaml`, macos-latest): checks out exactly `repo-commit` into `_repo/`, runs `scripts/test.sh`, builds with `LOGIX_ENGINE_VERSION` = the release tag, packs `logix-engine-darwin-arm64-<package tag>.tgz` (one `logix-engine/` folder with the binary and `LICENSE`), and checks that the packed binary reports the release tag and has an ad-hoc signature.
  - `pre-release` (Ubuntu): virus scan, release notes (what the engine is, that these are development builds, macOS steps with `xattr -c`, trying it with `claude mcp add`, the packages table, build info, about these releases), keeps the 5 newest pre-releases, replaces a same-tag pre-release, publishes the `.tgz` and `BUILD-INFO.json`.
- Add Linux and Windows as `build-<platform>.yaml` and test matrix entries when those platforms are implemented.

## Rules that are easy to break

- **stdout is only for MCP.** Logs and tool output go to the log file and stderr, never stdout.
- **The tool API and command line never break** after the first release. Changes only add tools, optional fields or arguments. A breaking change gets a new tool name.
- **Stateless requests.** Every request carries its own folders and board. The engine never reads host project files or merges catalog definitions from disk. Requests never carry source text.
- **Safe file changes.** Check the path keyword rules, resolve symbolic links, and refuse forbidden locations before any disk change. The engine writes only in the engine folder and build folders, plus in-place rewrites of named source files when an operation calls for it, such as formatting, and generated files the request names, such as simulate's default GTKWave layout, replaced or deleted only while they carry the generated-file marker.
- **Build folders are disposable.** Deleting one never loses data, and the next operation that writes to it creates it again, with the same result. Never keep anything in a build folder that can't be generated again. A test checks a rebuild after a delete.
- **Match criteria are internal.** How a device's match level is decided never appears in the tool API, tool descriptions or messages to hosts, and can change in any version. Hosts get only the level (and later, an explanation for people to read as is).
- **Errors are data.** Use the six error categories and the suggested action codes from the tool API. A failing test or missed timing is a result, not an error. Messages never assume a particular host.
- **Schemas come from Rust types.** Don't hand-write JSON schemas. Every tool and field needs a clear, self-contained description, because AI agents learn the tools from them alone.
- **No network at startup, no silent upgrades.** Network access happens only to install or repair packages an operation needs, or when a host asks.
- **Date versions.** Canonical form `yyyy-mm-dd`. Compare by date, never as mixed-form strings.

## How work is done here

The human directs the work and tests the results. Claude writes and maintains the code, the tests and the docs. Humans don't review every line, so:

- Add or update tests with every change. Tests are the main guard against regressions.
- Keep external interfaces, requirements and docs simple and easy for people to understand. Code readability matters less than correctness and test coverage.
- Update the docs in `docs/` in the same change as the code they describe. If code and docs disagree, ask which one is right.
- Record open questions in the relevant doc's "Open questions" section, or as a GitHub issue if the user asks.
